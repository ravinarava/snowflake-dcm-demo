# Snowflake DCM CI/CD Code Walkthrough

This document explains the current repository line by line and follows the execution path from a GitHub event to Snowflake.

The repository combines:

- GitHub Actions for automation and identity.
- Terraform for the foundation layer.
- Snowflake DCM for database objects.
- GitHub OIDC for passwordless authentication.

## 1. Repository Execution Model

The project has three execution paths:

```text
Pull request or manual validation
  -> ci-validation.yml
  -> validation.yml
  -> Terraform plan and DCM plan

Manual DEV deployment
  -> deploy-dev.yml
  -> Terraform import, plan, and apply
  -> DCM deploy DEV

Manual TEST deployment
  -> deploy-test.yml
  -> Terraform import, plan, and apply
  -> DCM deploy TEST
```

The ownership boundary is:

```text
Bootstrap SQL       -> creates workload users and roles
Terraform           -> manages foundation infrastructure
Snowflake DCM       -> manages database objects
GitHub Actions      -> authenticates and orchestrates execution
```

## 3. Bootstrap Identity File

File: `bootstrap/snowflake/01-identities.sql`

This script is executed once by an administrator-controlled Snowflake session. It creates the workload identities used by GitHub Actions.

### Lines 1-4: Terraform and DCM roles

```sql
CREATE ROLE IF NOT EXISTS GITHUB_DEV_TERRAFORM_ROLE;
CREATE ROLE IF NOT EXISTS GITHUB_DEV_DCM_ROLE;
CREATE ROLE IF NOT EXISTS GITHUB_TEST_TERRAFORM_ROLE;
CREATE ROLE IF NOT EXISTS GITHUB_TEST_DCM_ROLE;
```

`CREATE ROLE IF NOT EXISTS` makes the script repeatable. If the role already exists, Snowflake does not fail because of a duplicate object.

The names encode both environment and responsibility:

- `DEV` or `TEST` identifies the environment.
- `TERRAFORM` identifies the foundation owner.
- `DCM` identifies the object-layer owner.

### Lines 6-17: Service users

```sql
CREATE USER IF NOT EXISTS GITHUB_DEV_TERRAFORM_SVC
  TYPE = SERVICE;
```

This creates a service user for DEV Terraform authentication. `TYPE = SERVICE` indicates that this is an automation identity rather than a human user.

The same pattern creates:

```text
GITHUB_DEV_DCM_SVC
GITHUB_TEST_TERRAFORM_SVC
GITHUB_TEST_DCM_SVC
```

No password or private key is created here. Authentication is intended to happen through GitHub OIDC and Snowflake workload identity.

### Lines 19-30: Role assignments

```sql
GRANT ROLE GITHUB_DEV_TERRAFORM_ROLE
  TO USER GITHUB_DEV_TERRAFORM_SVC;
```

This assigns the DEV Terraform role to the DEV Terraform service user.

The remaining statements perform the equivalent assignments for DEV DCM, TEST Terraform, and TEST DCM.

This script creates identity structure, but it does not yet grant the final least-privilege Snowflake permissions. Those privileges must be designed and granted separately.

## 5. DCM Object Definitions

DCM reads the SQL definitions under `sources/definitions` and compares them with the Snowflake target.

### `database.sql`

```sql
DEFINE SCHEMA DEMO_DB.RAW;
DEFINE SCHEMA DEMO_DB.CURATED;
DEFINE SCHEMA DEMO_DB.STAGING;
```

Each statement declares a schema:

- `RAW` is intended for source or unprocessed data.
- `CURATED` is intended for prepared analytical data.
- `STAGING` is intended for intermediate processing.

### `roles.sql`

```sql
DEFINE ROLE DATA_ENGINEER_ROLE;
DEFINE ROLE DATA_ANALYST_ROLE;
```

These are DCM-managed object-layer roles. They are separate from the GitHub service roles used to run automation.

### `tables.sql`

```sql
DEFINE TABLE DEMO_DB.RAW.CUSTOMERS (
CUSTOMER_ID NUMBER,
CUSTOMER_NAME VARCHAR
);
```

The fully qualified table name is `DEMO_DB.RAW.CUSTOMERS`.

The columns are:

- `CUSTOMER_ID NUMBER`: numeric customer identifier.
- `CUSTOMER_NAME VARCHAR`: customer name.

### `grants.sql`

```sql
GRANT USAGE ON DATABASE DEMO_DB TO ROLE DATA_ENGINEER_ROLE;
GRANT USAGE ON SCHEMA DEMO_DB.RAW TO ROLE DATA_ENGINEER_ROLE;
GRANT USAGE ON SCHEMA DEMO_DB.CURATED TO ROLE DATA_ANALYST_ROLE;
```

The first statement allows the engineering role to use the database.

The second allows engineers to use the RAW schema.

The third allows analysts to use the CURATED schema.

These statements demonstrate role-based access as code.

### `warehouse.sql`

```sql
DEFINE WAREHOUSE TRANSFORM_WH
WAREHOUSE_SIZE='XSMALL'
AUTO_SUSPEND=60
AUTO_RESUME=TRUE;
```

This defines a small transformation warehouse:

- `WAREHOUSE_SIZE='XSMALL'` limits compute size.
- `AUTO_SUSPEND=60` suspends it after 60 seconds of inactivity.
- `AUTO_RESUME=TRUE` starts it when work arrives.

## 6. Terraform Version Constraints

File: `terraform/versions.tf`

```hcl
terraform {
    required_version = ">= 1.5.0, < 2.0.0"

    required_providers {
        snowflake = {
            source = "snowflakedb/snowflake"
            version = "~> 2.0"
        }
    }
}
```

### `terraform {}` block

This is Terraform's top-level configuration block.

### `required_version`

```hcl
required_version = ">= 1.5.0, < 2.0.0"
```

This allows Terraform 1.x versions from 1.5 onward, but prevents an automatic move to Terraform 2.x.

The GitHub deployment workflows currently pin Terraform to version `1.9.8`, which satisfies this constraint.

### `required_providers`

This declares providers needed by the configuration.

### `source`

```hcl
source = "snowflakedb/snowflake"
```

This tells Terraform where to download the Snowflake provider.

### `version`

```hcl
version = "~> 2.0"
```

This permits compatible Snowflake provider 2.x releases. The selected provider version and checksums are recorded in `.terraform.lock.hcl`.

### `provider "snowflake"`

### `authenticator`


This tells the provider to use workload identity rather than a password or key pair.

### `account_name` and `organization_name`

## 11. GitHub Workflow Caller

File: `.github/workflows/ci-validation.yml`

This file is the public validation entry point. It chooses which environment to validate and calls the reusable implementation.

### Workflow name

```yaml
name: CI Validation
```

This is the name shown in GitHub Actions.

### Pull request trigger

```yaml
on:
  pull_request:
    branches:
      - main
```

A pull request targeting `main` triggers validation.

### Manual trigger

```yaml
workflow_dispatch:
  inputs:
    validation_environment:
      description: Environment to validate
      required: true
      type: choice
      default: DEV
      options:
        - DEV
        - TEST
```

A user can manually choose DEV or TEST from the GitHub Actions UI.

### Permissions

```yaml
permissions:
  contents: read
  id-token: write
```

`contents: read` permits repository checkout.

`id-token: write` permits GitHub to issue an OIDC token to the job.

### Concurrency

```yaml
concurrency:
  group: snowflake-validation-${{ github.event_name }}-${{ inputs.validation_environment || 'DEV' }}
  cancel-in-progress: false
```

This prevents overlapping validation runs for the same event/environment group. `cancel-in-progress: false` allows the existing run to finish instead of cancelling it.

### DEV caller

```yaml
validate-dev:
  if: github.event_name == 'pull_request' || inputs.validation_environment == 'DEV'
  uses: ./.github/workflows/validation.yml
```

The DEV job runs when:

- The event is a pull request, or
- A manual run selects DEV.

The `uses` line calls the reusable workflow rather than duplicating its steps.

The inputs are:

```yaml
environment_name: DEV
dcm_target: DEV
terraform_user: GITHUB_DEV_TERRAFORM_SVC
dcm_user: GITHUB_DEV_DCM_SVC
terraform_var_file: environments/dev.tfvars
```

These values select the GitHub environment, DCM target, OIDC users, and Terraform values.

### TEST caller

```yaml
validate-test:
  if: github.event_name == 'workflow_dispatch' && inputs.validation_environment == 'TEST'
  uses: ./.github/workflows/validation.yml
```

TEST validation only runs when manually selected. It does not run automatically for every pull request.

Its identity mapping is:

```yaml
terraform_user: GITHUB_TEST_TERRAFORM_SVC
dcm_user: GITHUB_TEST_DCM_SVC
terraform_var_file: environments/test.tfvars
```

### Explicit secret passing

```yaml
secrets:
  SNOWFLAKE_ACCOUNT: ${{ secrets.SNOWFLAKE_ACCOUNT }}
```

Only the required Snowflake account secret is passed into the reusable workflow. This is narrower than `secrets: inherit`.

## 12. Reusable Validation Workflow

File: `.github/workflows/validation.yml`

This file contains the common validation implementation for DEV and TEST.

### `workflow_call`

```yaml
on:
  workflow_call:
```

This means the workflow is called by another workflow instead of being triggered directly.

### Inputs

The reusable workflow requires:

```yaml
environment_name
dcm_target
terraform_user
dcm_user
terraform_var_file
```

Each input is required and typed as a string.

### Secret contract

```yaml
secrets:
  SNOWFLAKE_ACCOUNT:
    description: Snowflake account identifier
    required: true
```

The reusable workflow explicitly declares the one secret it needs.

### Input validation job

```yaml
validate-inputs:
  runs-on: ubuntu-latest
  timeout-minutes: 10
```

This job validates the environment, target, identities, and variable-file combination before Snowflake commands run.

The shell variables copy GitHub inputs into environment variables:

```yaml
ENVIRONMENT_NAME: ${{ inputs.environment_name }}
DCM_TARGET: ${{ inputs.dcm_target }}
TERRAFORM_USER: ${{ inputs.terraform_user }}
DCM_USER: ${{ inputs.dcm_user }}
TERRAFORM_VAR_FILE: ${{ inputs.terraform_var_file }}
```

The shell uses:

```bash
set -euo pipefail
```

This makes the script fail on command errors, unset variables, and pipeline errors.

The `case` statement allows only these exact combinations:

```text
DEV  + DEV  + GITHUB_DEV_TERRAFORM_SVC  + GITHUB_DEV_DCM_SVC  + environments/dev.tfvars
TEST + TEST + GITHUB_TEST_TERRAFORM_SVC + GITHUB_TEST_DCM_SVC + environments/test.tfvars
```

This prevents accidental combinations such as TEST target with DEV identity.

### Terraform plan job

The Terraform job depends on input validation:

```yaml
needs: validate-inputs
```

It selects the GitHub environment dynamically:

```yaml
environment:
  name: ${{ inputs.environment_name }}
```

Its environment variables are:

```yaml
SNOWFLAKE_ACCOUNT: ${{ secrets.SNOWFLAKE_ACCOUNT }}
SNOWFLAKE_USER: ${{ inputs.terraform_user }}
SNOWFLAKE_WORKLOAD_IDENTITY_PROVIDER: OIDC
```

The Snowflake action receives the OIDC token configuration:

```yaml
- uses: snowflakedb/snowflake-actions@v3
  with:
    use-oidc: true
```

The identity check runs before Terraform:

```yaml
snow sql -q "select CURRENT_USER(), CURRENT_ROLE(), CURRENT_ACCOUNT()" -x
```

This confirms which Snowflake user, role, and account are active.

Terraform is installed with the wrapper disabled:

```yaml
- uses: hashicorp/setup-terraform@v3
  with:
    terraform_wrapper: false
```

The wrapper is disabled so Terraform command output and behavior remain direct and predictable.

Terraform initializes in its directory:

```yaml
working-directory: terraform
run: terraform init -input=false
```

`-input=false` prevents an interactive prompt from hanging CI.

The temporary import step checks whether Terraform already knows the role:

```bash
if terraform state show snowflake_account_role.tf_platform_role > /dev/null 2>&1; then
  echo "Foundation role is already in Terraform state"
else
  terraform import -input=false \
    -var-file="${{ inputs.terraform_var_file }}" \
    snowflake_account_role.tf_platform_role TF_PLATFORM_ROLE_V1
fi
```

If the resource exists in local state, no import is attempted. Otherwise, the existing Snowflake role is imported using the selected environment values.

This step is temporary. It is needed because GitHub-hosted runners do not retain local state between runs.

Terraform validation runs next:

```yaml
terraform validate
```

The format check runs next:

```yaml
terraform fmt -check -recursive
```

The plan uses the selected environment file:

```bash
terraform plan -input=false -no-color \
  -var-file="${{ inputs.terraform_var_file }}"
```

### DCM plan job

The DCM job also depends on input validation:

```yaml
needs: validate-inputs
```

It uses the selected environment and DCM identity.

After OIDC setup, it verifies the Snowflake session, then runs:

```bash
snow dcm plan --target "${{ inputs.dcm_target }}" -x
```

For DEV, the target is DEV. For TEST, the target is TEST.

## 13. DEV Deployment Workflow

File: `.github/workflows/deploy-dev.yml`

### Trigger and permissions

```yaml
on:
  workflow_dispatch:
```

DEV deployment is manual.

```yaml
permissions:
  id-token: write
  contents: read
```

The workflow can checkout code and request OIDC.

### Concurrency

```yaml
concurrency:
  group: snowflake-deploy-dev
  cancel-in-progress: false
```

Only one DEV deployment can run at a time.

### DEV Terraform environment

```yaml
environment:
  name: DEV
```

This connects the job to the GitHub DEV environment and its protection rules/secrets.

```yaml
SNOWFLAKE_USER: GITHUB_DEV_TERRAFORM_SVC
SNOWFLAKE_WORKLOAD_IDENTITY_PROVIDER: OIDC
```

The Terraform job uses the DEV Terraform workload user.

### DEV setup sequence

The steps are:

1. Checkout the repository.
2. Configure Snowflake OIDC.
3. Verify the Terraform identity.
4. Install Terraform 1.9.8.
5. Initialize local Terraform state.
6. Import the existing foundation role if needed.
7. Generate a Terraform plan file.
8. Apply the exact generated plan.

The pinned setup is:

```yaml
- uses: hashicorp/setup-terraform@v3
  with:
    terraform_version: 1.9.8
    terraform_wrapper: false
```

The plan is generated with:

```bash
terraform plan -input=false -no-color \
  -out=tfplan \
  -var-file=environments/dev.tfvars
```

The saved plan is applied with:

```bash
terraform apply -input=false tfplan
```

This is safer than generating a new plan during apply.

### DEV DCM deployment

The DCM job waits for Terraform:

```yaml
needs: terraform-apply
```

It uses:

```yaml
SNOWFLAKE_USER: GITHUB_DEV_DCM_SVC
```

After identity verification, it runs:

```bash
snow dcm deploy --target DEV -x
```

The foundation layer is therefore applied before the object layer is deployed.

## 15. Complete DEV Execution Walkthrough

### Pull request validation

1. A pull request targets `main`.
2. GitHub starts `ci-validation.yml`.
3. The DEV caller is selected because the event is `pull_request`.
4. The caller invokes `validation.yml`.
5. The reusable workflow validates the DEV input combination.
6. The Terraform job starts in the DEV GitHub environment.
7. GitHub issues an OIDC token.
8. Snowflake Action configures workload identity.
9. The workflow verifies the Snowflake user and role.
10. Terraform initializes.
11. The existing platform role is imported into temporary state if needed.
12. Terraform validates formatting and configuration.
13. Terraform creates a DEV plan.
14. The DCM job authenticates as `GITHUB_DEV_DCM_SVC`.
15. DCM creates a DEV plan.
16. Reviewers see Terraform and DCM previews without deployment.

### Manual DEV deployment

1. A user starts `deploy-dev.yml`.
2. The workflow uses the DEV GitHub environment.
3. Terraform authenticates as `GITHUB_DEV_TERRAFORM_SVC`.
4. The existing role is imported if necessary.
5. Terraform generates `tfplan`.
6. Terraform applies `tfplan`.
7. The DCM job waits for Terraform success.
8. DCM authenticates as `GITHUB_DEV_DCM_SVC`.
9. DCM deploys the DEV target.

## 18. Current Limitations

The current repository is production-shaped but has known deferred items:

1. Terraform state is local and temporary. S3 is planned.
2. The dedicated Terraform roles exist, but their final least-privilege grants are not yet verified.
3. DEV and TEST target the same Snowflake account and database.
4. Both environments manage the same `TF_PLATFORM_ROLE_V1` resource.
5. The import workaround remains until persistent state is introduced.
6. GitHub environment approval rules must be configured in repository settings.
7. GitHub Actions are pinned by major version, not commit SHA.
8. The bootstrap file creates identity structure but does not define all least-privilege grants.

These limitations do not prevent a controlled demo, but they should be resolved before unattended production deployments.

## 19. Recommended Production Sequence

```text
1. Configure GitHub DEV and TEST environments.
2. Verify Snowflake OIDC subject mappings.
3. Verify CURRENT_USER and CURRENT_ROLE in each workflow.
4. Replace ACCOUNTADMIN with least-privilege Terraform roles.
5. Grant least-privilege DCM permissions.
6. Decide whether DEV and TEST need separate databases/accounts.
7. Give each Terraform state owner a unique resource set.
8. Add the S3 backend and state locking.
9. Remove repeated import steps after state migration.
10. Pin GitHub Actions to verified commit SHAs.
11. Add secret scanning and Terraform security scanning.
12. Add protected environment approvals.
```

## 20. Presentation Summary

This repository demonstrates a two-layer Snowflake delivery model. GitHub Actions supplies short-lived OIDC identity and orchestrates the workflow. Terraform manages the foundation role, while Snowflake DCM manages schemas, tables, roles, grants, and warehouses. Pull requests run DEV validation by default, manual validation can select TEST, and manual deployments apply Terraform before deploying the matching DCM target. Environment-specific workload users and `.tfvars` files prevent DEV and TEST configuration from being mixed accidentally.
