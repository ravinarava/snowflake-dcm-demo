01 // The big picture

Three layers, one delivery path.

The repository makes ownership visible. Automation is the connective tissue; Terraform and DCM each have a clear job.

01

GitHub Actions

Runs pull-request validation and manual deployment workflows. It also requests the short-lived OIDC identity.

02

Terraform

Owns foundation infrastructure such as service users, integrations, policies, and platform roles.

03

Snowflake DCM

Owns the object layer: schemas, tables, warehouses, roles, grants, tasks, and streams.

02 // Data platform as code

The object layer reads like a blueprint.

Definitions under sources/definitions express the desired Snowflake state declaratively.

sources/definitions/database.sql

Database schemas

The project establishes a simple raw-to-curated shape.

DEFINE SCHEMA DEMO_DB.RAW;
DEFINE SCHEMA DEMO_DB.CURATED;
DEFINE SCHEMA DEMO_DB.STAGING;
sources/definitions/roles.sql

Role boundaries

Access is split between engineering and analytics personas.

DEFINE ROLE DATA_ENGINEER_ROLE;
DEFINE ROLE DATA_ANALYST_ROLE;
sources/definitions/tables.sql

Business data

The demo table is a deliberately small customer model in the raw layer.

DEFINE TABLE DEMO_DB.RAW.CUSTOMERS (
  CUSTOMER_ID NUMBER,
  CUSTOMER_NAME VARCHAR
);
sources/definitions/grants.sql

Permissions as code

Grants show how roles receive only the schema access they need.

GRANT USAGE ON SCHEMA DEMO_DB.RAW
  TO ROLE DATA_ENGINEER_ROLE;
GRANT USAGE ON SCHEMA DEMO_DB.CURATED
  TO ROLE DATA_ANALYST_ROLE;
sources/definitions/warehouse.sql

Compute policy

The transformation warehouse is small, inexpensive, and automatically managed.

AUTO_SUSPEND=60
AUTO_RESUME=TRUE;

03 // Foundation layer

Terraform lays the platform tracks.

The current implementation is intentionally minimal, while the module structure points toward a larger foundation layer.

terraform/main.tf

One managed role

The active Terraform resource is the platform role below.

resource "snowflake_account_role"
  "tf_platform_role" {
  name = "TF_PLATFORM_ROLE_V1"
}
terraform/providers.tf

Passwordless provider

The Snowflake provider uses workload identity and currently targets the account with ACCOUNTADMIN.

authenticator = "WORKLOAD_IDENTITY"
account_name = "AL32991"

terraform/modules/*

Planned extension points

Module folders exist for network policies, security integrations, storage integrations, and users. They are currently empty or not wired into main.tf. variables.tf is also empty, so environment values are not parameterized yet.

04 // Identity without long-lived secrets

GitHub proves who is running.

OIDC gives each job a short-lived identity token. Snowflake maps that identity to a specific workload user.

01

GitHub grants token permission

Each workflow declares id-token: write, allowing GitHub Actions to request an OIDC token.

02

Snowflake Action configures auth

snowflakedb/snowflake-actions@v3 runs with use-oidc: true and prepares the CLI environment.

03

User identity must match

SNOWFLAKE_USER must match the Snowflake user associated with the authenticated workload identity. A mismatch produces the LOGIN_NAME error.

04

Commands run passwordlessly

Terraform and DCM use the authenticated Snowflake session without storing a long-lived password in the repository.

05 // Pull-request confidence

Plans before changes.

.github/workflows/ci-validation.yml gives reviewers two views of an incoming change.

terraform-plan

Infrastructure preview

Checks out the repository, authenticates with OIDC, initializes Terraform, validates the configuration, and runs a plan.

terraform init Prepare providers
terraform validate Check syntax
terraform plan Preview foundation changes
dcm-plan

Object preview

Runs the DCM plan command against DEV so reviewers can see the proposed database and data-object changes before deployment.

snow dcm plan --target DEV -x

08 // Know the edges

What is real today, and what comes next.

These caveats make the demo credible and give the audience a clear roadmap.

Small Terraform surfaceOnly one account role is currently active, despite the broader architecture plan.
Ephemeral stateNo remote backend is configured. Workflows import the existing role before apply.
Shared accountDEV and TEST currently point to the same Snowflake account and DCM project.
Least privilegeThe provider uses ACCOUNTADMIN today. Production should use scoped administrative roles.
Empty modulesFoundation module folders exist as planned extension points but are not wired in.
Future identitiesA mature design could separate DEV/TEST Terraform and DCM service users.
Unparameterized valuesvariables.tf is empty, so account and environment settings are not yet configurable.
Reserved db layoutThe db folders are empty; current active definitions live under sources/definitions.
Closing statement

This project demonstrates a two-layer Snowflake deployment architecture. Terraform manages the foundation layer, while Snowflake DCM manages databases, schemas, tables, roles, grants, and warehouses. GitHub Actions provides CI validation and deployment automation. Authentication uses GitHub OIDC and Snowflake workload identity, so the workflows do not require long-lived passwords.
